# 04. 横断ドメインモデルと責務の境界

この文書は、複数の機能・処理経路にまたがる 8 つの基本概念について、定義・不変条件・現状の実装上の所在・目標とする所有境界を整理する。
個別のデータ形式は [02-data-model.md](02-data-model.md)、同期手順は [03-sync-and-concurrency.md](03-sync-and-concurrency.md)、署名と台帳権限は [11-security.md](11-security.md) を参照する。

> **注記（現状と目標の区別）**：本書の「現状」は現在のコードベースの事実を示し、「目標とする所有境界」は今後リファクタリングで収束させるべき境界（未採用の監査提案 [2026-11-11/architecture.md](audits/2026-11-11/architecture.md) ARC-01〜05 と整合する整理方針）を示す。未実装の型や境界を現行コードに存在するかのように扱ってはならない。

## 1. 横断概念の一覧

| 概念 | 定義 | 不変条件・守るべき区別 | 現状の実装と分散箇所 | 目標とする所有境界 |
|---|---|---|---|---|
| **履歴** | 対象 ref のコミットチェーンに記録されたイベント列 | ・不変の追記履歴であり、後から書き換えない<br>・受理前に封筒形式、ref/entity 一致、データ契約、ID 一意性、順序規則を満たす | `initapp`、`syncapp/event_ids.go`、`entitychain`、`verifyapp` がそれぞれ個別に検査を組み立てている | 単一の履歴受理境界が「完全履歴 / shallow / 未検証」の区別を伴って受理判定を行う |
| **状態** | イベント列を `fold` して得られるエンティティの現在状態、およびそのツリー表現 | ・正本はイベント履歴であり、実体化ツリーやスナップショットは派生結果である<br>・閲覧用スナップショット（shallow 時の `meta.json` 等）を完全履歴から検証した状態と混同しない | `core/materialize` が純粋関数として `fold` を持ち、`snapshotread` がツリー直読みを行う | `Materializer` が純粋 `fold` を所有し、完全履歴由来の状態と snapshot 由来の閲覧ビューを型または明示属性で区別する |
| **検証** | 履歴・署名・台帳・チェックポイントが期待契約を満たしているかの判定 | ・「何を検証したか（形式 / 順序 / 実体化一致 / 署名・台帳）」を単一の `verified=true` に丸めない<br>・`meta/config` 不在（day0）と既存 `config.json` 破損を区別する | `verifyapp`、`fsckapp`、`entitychain`、`syncapp` に検査が分散 | 検証対象・適用した設定/台帳 OID・検証項目を束ねた結果として返し、入口ごとの漏れをなくす |
| **操作** | 利用者（人間または AI）が意図した 1 つのコマンド単位 | ・1 つの利用者操作を成立させる複数処理（例：作成＋リンク、副作用の計画）の順序と調停は途中で分断しない | 一部の複合処理がクライアント層（`cmd/githive/task.go` と `cmd/githive/mcp.go` の作成＋リンク等）に残っている | `internal/app` のコマンドが操作全体の調停を所有し、クライアント層は入力受付と出力整形のみを行う |
| **保存成功** | ローカルのリポジトリ（Git オブジェクトおよび対象 ref）に新しいコミットが記録された事実 | ・ネットワーク失敗でローカル保存の成功を取り消さない<br>・ただし、ローカル保存後に別履歴を採用して ref が差し替わった場合は「保存済みだが現在 ref からは外れた」事実を区別する（[ADR-0033](adr/0033-local-registry-recovery-and-publication-outcomes.md)） | `entitychain.Writer` が CAS 再試行付きで保存するが、操作結果の表現はコマンド・adapter ごとに異なる | `app` が「ローカル保存の成否」「現在 ref での保持」「退避先」を構造化した結果で返し、CLI/MCP が同じ意味で出力する |
| **同期成功** | ローカルの履歴をリモートと突き合わせ、取得・マージ・配送した結果 | ・「ローカル保存の成功」と「リモートへの配送完了」を混ぜない<br>・一部の ref のみ成功・一部失敗（部分成功）を失敗や完全成功へ丸めない | `syncapp` が per-ref 結果を返すが、呼び出し側の adapter（`cmd/githive/root.go` 等）で一部情報が落ちる経路がある | `syncapp` と `app` の共通結果モデルが per-ref の配送状態・警告・回復情報を保持し、全クライアントがそのまま伝える |
| **同一性** | エンティティ ID、イベント ID、操作 ID、および Git コミット OID の区別 | ・エンティティ ID（ref 対象）、イベント ID（ULID、辞書順キー）、コミット OID（履歴位置）を混同しない<br>・同一テキストの再実行と、同一操作の冪等リトライを混同しない | エンティティ ID とイベント ID は `core/idgen`・`core/event` で管理。操作単位の冪等 ID は未導入 | エンティティ・イベント・コミット OID の対応を明示し、将来の操作冪等キー導入時は `app` 層で一元管理する |
| **信頼** | SSH 署名、信頼の根（trust-root pin）、ユーザー台帳（`users/registry`）、権限の関係 | ・署名検証の成否と、台帳履歴の完全性（完全 / shallow / 破損 / なし）と、データ内容の正しさを混同しない<br>・台帳検証に使った OID と参照に使う OID を分離しない | `core/sign`、`verifyapp`、`usersapp`、個別機能（`workpackageapp` 等）が参照する | 台帳の検証状態と評価時点の OID・pin を結び付け、権限・承認判定を行う全機能が同じ健全性区分を使う |

## 2. 設計判断に使うルール

- 新しい検査条件や制約を追加するときは、「呼び出し元の一部だけに `if` を足す」のではなく、上表のどの概念の責務かを特定し、その所有境界に配置する。
- 2 つ以上の機能（例：`issue` と `task`、`CLI` と `MCP`）で上表の同じ概念・不変条件を扱う場合は、実装箇所が少なくても処理を複製せず `app` または `core` の共有境界へ寄せる（[AGENTS.md](../AGENTS.md) 原則 3）。
- 未確認・未検証・取得失敗を、暗黙の空値や `nil` で「問題なし」に変換しない。
