# 補償コード監査と第一原理の再設計案

この監査は、PRレビュー・Issue修正・ソースレビューと並行して行った。**再設計は提案であり未採用。既存の不具合修正を提案の採用待ちにしない。**

「補償コード」は、別の責務で失われた情報、二重の状態、曖昧な同一性、不十分な入力契約を、後段の fallback・再試行・復元・例外変換で埋める実装として調べた。分散更新、ネットワーク切断、不可信な Git 入力そのものは消えないため、CAS・必要な再試行・署名検査・所有資源の後始末まで一律に削除対象とはしない。

## 結果の読み方

- [core の実装とテスト](core.md): イベント順序、鍵同一性、checkpoint、汎用状態と復元、Git adapter、必要な競合制御。
- [app の実装](app.md) / [app テストの構造](app-tests.md): 受理経路、設定、同期、複合操作、通知、Wiki の回復。
- [CLI/MCP と出力境界](boundaries.md) / [境界テストの構造](boundary-tests.md): ID/型変換、部分結果、警告、成功の意味。
- [scripts・CI・開発補助](scripts.md): 検証対象の固定、環境補正、誤った PASS を防ぐ条件。
- [第一原理の設計案](architecture.md): 正・順序・信頼・保存・配送の所有を整理する案と、現形式では消せない補償。
- [設計案の独立レビュー](design-review.md): cache の証拠、操作同一性、旧 writer、履歴移行、mutable state の所有に関する未決条件。

## 第一原理から変える点

1. **受理済み履歴を一つの概念にする。** 正確な OID、契約版、検査範囲を保持し、init/sync/append/read が別々に「正」を推測しない。完全履歴と未検証 snapshot を別の型・結果として扱う。
2. **利用者操作の結果を app が所有する。** ローカル保存、現在 ref への残存、副作用、配送、競合・回復を一つの結果に保持する。CLI/MCP が一部を捨てて成功へ丸める余地を減らす。
3. **派生状態を正にしない。** 型付き状態から Markdown/JSON を投影する。checkpoint/cache は独立した証拠が揃う場合にだけ再利用し、自己申告の hash を検証済みとしない。
4. **ID・時刻・因果・鍵の表示文字列を分ける。** 根本的に時計ずれ拒否や鍵文字列表現の補償をなくすには、次版で causal dependency / 安定 KeyID を設計する必要がある。既存の署名済み履歴を無言で並べ替えない。
5. **必要な障害処理は保持する。** Git CAS、輸送失敗、部分受理、所有する worktree だけの削除は、責務を整理しても必要。単一 journal/manifest は比較案であり、複雑さを移しただけで改善とは数えない。

[追加ファイルとinventory照合](coverage-addendum.md)を含め、各分担報告は観測した commit と file coverage ledger を持つ。production は意味的な経路確認、tests は構造確認と実行した試験を区別する。第三者依存の全実装、全OS・全locale・全入力の証明、将来formatの完成はこの監査の対象ではない。既知の不具合・修正の対応は以下の再評価に記録する。

## 並行する main 更新の取り込み

監査後に main が `7d09d0e3e69a31534c4510d9eac21211177c73db` へ更新され、8件のPR squashを含む履歴になった。`c1ec754` で取り込み、競合を領域別に独立確認した。Goの全279ファイルは取り込み前と同じ内容を保持し、差分はrelay関連6ファイルに限定された。新しいmain側の内容を忘れず、設定/履歴/署名/保存/部分結果の追加保護も維持している。
