# ADR-0026: 実体化から黙って消える書き込みと create の置換を拒否する

## 状態

採用（Issue #88 の保存・取り込み境界の保護）

## 背景

現在の issue/task/chat reducer は ID 順で create より前に並ぶ変更を無視する。作成者の時計が先行していると、別の端末が生成したコメントの ID が create より小さくなり、保存は成功しても本文が実体化されない。users の鍵操作も、その前提となる登録より先に並ぶと無視される。

## 決定

- 通常のアプリケーション追記では、新しい変更イベントの ID が、既知の非 checkpoint イベントの最大 ID 以下なら、コミット・ref 更新前に `clock_skew` で失敗する。既存イベントの ID や時刻は変更せず、自動的な因果 ID への置換も行わない。
- `clock_skew` は環境不備（CLI 終了コード 5）、機械的な再試行不可とし、既知の ID・時刻と復旧案内を返す。利用者は自端末と元の端末の時計を確認し、新しい ID が既知の履歴より後になる状態で元の操作を再実行する。
- 同じ ID に異なる canonical payload がある場合は、既存の `conflicting_event_id` を先に返す。時計保護で衝突を隠さない。
- 生の issue/task/chat 履歴の取り込みでは、同じ feature/entity の異なる create が複数ある場合、または既存 create より前の変更がある場合を `event_order_violation` として拒否する。読み取り・同期・マージの境界で検査し、fsck/verify にも問題を表示する。元のコミットやイベントは書き換えない。
- checkpoint は変更イベントの順序制約から除外する。同一内容の create の複製は従来どおり ID で重複排除する。
- create 後の有効なイベントが生の履歴で順不同に届くことは引き続き許容する。reducer、ID 順ソート、Go/Python の fold、既存ゴールデンベクタは変更しない。既存の create 制約を保存・受け入れ境界で強制するため、schema_version は昇格しない。

## 制限

新しい ID を既知の最大値より後へ自動生成する機構は導入しない。そのため時計が大きく先行した既存履歴への追記は、時計の確認・修正または時刻の経過を待つ必要がある。同一ミリ秒でも別プロセスの乱数部の大小で新しい ID が小さくなる場合は拒否するため、時刻が進んだ後に再実行する。

本決定で残した users の生の key_add/key_revoke と user_set の依存順序、およびコメント違いによる無視・鍵の重複は、[ADR-0027](0027-reject-ignored-users-key-events.md) の追加受け入れ検査で拒否する。通常のアプリケーション追記は引き続き共通の clock_skew 保護を受ける。create の無い断片だけから、架空の create や本文を生成することはしない。
