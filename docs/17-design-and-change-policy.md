# 17. 設計判断・変更・承認ポリシー

この文書は、githive における設計変更の判断基準、ADR の扱い、および Issue からマージまでの開発工程を定義する。
全エージェント共通の基本原則は [AGENTS.md](../AGENTS.md) を参照する。

## 1. 局所最適化と全体最適化の基準

タスクやバグ修正に着手するときは、次の基準で方針を選ぶ。

- **原因の所在で直す**：症状が出た箇所（CLI 表示、個別機能のハンドラ等）で場当たり的に握りつぶすのではなく、契約不備や責務漏れを起こしている層・コンポーネントを特定して直す。
- **既存パターンの無批判な模倣をしない**：既存の他機能が誤った層に処理を書いている場合（例：クライアント層での複合操作の組み立て）、新しい機能で同じ構造を複製しない。
- **既存設計の限界を見つけたら立ち止まる**：既存設計のままでは不変条件や責務分担を壊さずに実装できない場合、無理に例外分岐や補償コードを足さず、先に設計変更案（ADR）を提示する。

## 2. ADR（設計決定記録）のライフサイクル

設計変更や既存仕様が扱っていない前提の導入が必要な場合は、**実装コードを書く前に** `docs/adr/` へ ADR を追加する（`.claude/skills/adr/SKILL.md`）。

| 状態 | 意味 | 扱い |
|---|---|---|
| `検討中` | 新規に提案した直後の状態 | 実装の根拠にしてはならない。設計案としてレビューを受ける。 |
| `採用` | 権限者（リポジトリオーナー）の承認を得た状態 | 正規の設計判断として実装・レビューの根拠にする。 |
| `却下` | 検討したが採用しなかった案 | 理由を残すための記録。実装に使わない。 |
| `廃止` | 後続の採用済み ADR に置き換わった状態 | 置き換え先の ADR 番号を明記する。 |

### 同時更新の原則

「採用」となった ADR が既存の設計文書（`docs/01`〜`04`、`docs/10`〜`16`、`docs/features/*.md`）や `spec/` の内容を変更・上書きする場合、**ADR を追加する PR の中で対象文書の該当箇所も同時に更新する**。ADR を足しただけで本体文書を古いまま放置してはならない。

## 3. 開発ワークフロー（Issue 〜 マージ）

1. **Issue 起票**：目的、受け入れ条件、影響パッケージに加えて、関係するドメイン規則・設計契約・ADR 要否を明記する（`.github/ISSUE_TEMPLATE/`）。
2. **原因と影響範囲の分析**：表面的な現象ではなく根本原因を特定し、同じ責務・契約を共有する他機能やクライアント経路（CLI / MCP 等）を洗い出す。
3. **既存設計との整合性判定**：既存設計に沿って実装できるか、既存設計に欠陥があり修正を先行すべきかを判定する。
4. **設計決定・承認（必要時）**：設計変更が必要な場合は `検討中` の ADR を先に作成し、承認を得てから `採用` に進める。
5. **実装**：[AGENTS.md](../AGENTS.md) と [01-architecture.md](01-architecture.md) の責務分担・依存規則に従って実装する。
6. **全影響経路の検証**：変更箇所の単体テストだけでなく、共有境界を通る他機能・CLI/MCP 両経路・`spec/validate.py`・`internal/layering_test.go` を含む全ゲートを通す。
7. **PR レビュー・マージ**：仕様整合、責務分担、テスト妥当性を確認した上でマージする。

## 4. 並列作業時の競合判定

複数の Issue や作業を同時に進める場合、**変更するファイルパスの重複がないだけでは安全とみなさない**。次のいずれかが重なる場合は競合リスクありと判断し、直列に進めるか事前に契約を固定する。

- 同じドメイン概念（[04-domain-model.md](04-domain-model.md) の履歴・状態・検証・操作・同期・信頼等）の判定規則を変える変更
- 同じイベント封筒、スキーマ、`fold` 規則、エラーコード体系、または共有パッケージ（`entitychain`, `syncapp`, `verifyapp`, `core/*`）の契約を変える変更
